# 브라우저 E2E 검증 보고서

**대상 경로** 브라우저 입력 → `POST /api/call/turn` → 라우팅 → 응답 생성 → `to_dialect` → Typecast TTS
→ 브라우저 재생 → 통화 종료 → 민원카드 → 대시보드 반영
**일시** 2026-08-22 · **검증자** P7 (통화 UI)
**환경** macOS · Google Chrome 151 (headless) · 서버 `python3 -m server --port 8000`
**엔진 상태** 대화 `openai/gpt-5.6-luna` · STT `openai/gpt-4o-transcribe` · TTS `typecast` · `degraded: false`

> **먼저 밝힌다.** Claude 브라우저 확장(claude-in-chrome)이 이 머신에서 연결되지 않았다
> (`Browser extension is not connected` — 2회 시도 후 중단). 그래서 확장 기반의 대화형 클릭과
> `gif_creator` 녹화는 쓰지 못했다. 대신 **같은 Chrome 을 헤드리스로 띄워 실제 DOM 을 클릭·입력하며**
> 전 구간을 통과시켰고, 콘솔·네트워크·오디오·권한 호출을 페이지 안에서 계측했다.
> 확장이 필요한 항목(실시간 GIF 녹화)은 대체 방식을 썼고 아래에 명시한다.

## 2. 음성 재생 — 자동재생 정책

`audio_b64` 는 오는데 재생이 안 되는 경우를 확인하라는 지시였다. 실제로 **처음에는 전부 막혔다.**

```
NotAllowedError: play() failed because the user didn't interact with the document first
```

원인 분리:

- 헤드리스에서 스크립트가 부르는 `element.click()` 은 **사용자 활성화(user activation)로 인정되지 않는다.**
  즉 이 오류 자체는 자동화 환경의 산물이기도 하다.
- 그래서 두 가지를 나눠 확인했다.
  1. **오디오 데이터가 재생 가능한가** — `--autoplay-policy=no-user-gesture-required` 로 확인:
     `play()` 성공, `duration 4.5~7.6초`, `currentTime` 진행, `readyState 4`. **Typecast WAV 는 정상이다.**
  2. **정책에 걸리는 경우 어떻게 되는가** — 통화는 계속되고 텍스트는 그대로 보인다(무음 실패).

**조치(P7)** — 통화 버튼 클릭(진짜 사용자 제스처) 시점에 **무음 WAV 를 한 번 재생해 오디오 엘리먼트를 열어둔다.**
이후의 프로그램 재생은 정책에 걸리지 않는다. 그리고 그래도 막히면 조용히 삼키지 않고
`소리가 막혀 있니더. 화면을 한 번 누르시면 목소리가 나옵니더.` 를 띄우고 콘솔에 사유를 남긴다.

> 남은 한계: **진짜 사람이 클릭했을 때의 동작은 이 환경에서 증명하지 못했다.** 데모 전
> 한 번은 사람이 직접 눌러 소리가 나는지 확인해야 한다. (Chrome 은 한 번의 실제 클릭으로
> sticky activation 을 부여하므로 통과가 예상되지만, 예상은 증명이 아니다.)

## 3. 마이크 UI 상태 전이

| 확인 항목 | 결과 |
|---|---|

| 실패 후 상태 원복 | 녹음 표시 해제, 빈 말풍선 잔여물 없음, 텍스트 입력 계속 가능 |

## 5. 넘길 것 — 다른 소유 경로 (P7이 고치지 않았다)

### 5-1. P3 (`data/`, 크롤러) — 원문 데이터에 PUA 문자

`data/gb_departments.json` 에 글꼴 글리프가 없는 **사용자 정의 영역 문자 `U+F09E` 가 4곳** 있다.
전부 **`기후환경국 맑은물정책과`** — 배수·하수 민원이 배정되는 부서이고, **데모 시나리오가 정확히 그 부서로 간다.**
한컴/워드 기호 폰트의 글머리표가 그대로 넘어온 것으로 보인다.

```
◦ 하수도분야 국<U+F09E>도비 보조사업 예산 및 추진
◦ 하수도 재난<U+F09E>재해대책(호우, 태풍 등) 수립 및 시행
```

권고: 스크레이핑 단계에서 `U+E000–U+F8FF` 를 제거하거나 `·` 로 치환. 통화 UI 는 방어했지만
**대시보드(P8)도 같은 문자열을 그대로 렌더링**하므로 데이터에서 잡는 것이 옳다.

### 5-2. P6 (`server/`, `voisso/agent/`) — 두 가지

1. **`turn` 응답에 발신자 발화가 없다.** 이번 실행에서도 `caller_turn` / `caller_text` / `caller_standard`
   **전부 `null`** 로 확인했다(4턴 모두). `session.py::turn()` 은 `caller_dialect` 와
   `caller_standard = integrations.normalize(...)` 를 계산해 `self.transcript` 에 넣지만 응답에는 싣지 않는다.
   그래서 **"STT 원문 → 방언 정규화" 비교 화면이 실서버에서는 빈칸**이다(데모 스크립트 1단계 핵심 컷).
   `_say()` 반환 dict 에 아래 한 줄이면 UI 는 수정 없이 붙는다.

   ```python
   last = next((e for e in reversed(self.transcript) if e.get("role") == "caller"), None)
   "caller_turn": {"dialect": last["dialect"], "standard": last["standard"]} if last else None,
   ```

2. **세션이 메모리에만 있어 서버 재기동 시 통화가 끊긴다.** 검증 중 실제로 2회 발생했다
   (`POST /api/call/turn` 이 `status 0` 으로 끊긴 뒤 `end` 가 404 `세션을 찾을 수 없습니다`).
   원인은 다른 에이전트의 서버 재기동이었고 코드 결함은 아니다. 다만 **발표 중 누가 서버를 만지면
   진행 중인 통화가 그대로 죽는다.** 최소한 `end` 가 세션을 못 찾을 때 400/409 등으로 구분해 주면
   UI 가 더 정확히 안내할 수 있다. (`SESSION_TTL_SEC` 은 3600 으로 넉넉하다 — TTL 문제가 아니다.)

### 5-3. P8 (`web/dashboard/`) — 폴링은 정상

새 민원이 **1.2초** 만에 새로고침 없이 목록에 떴고 `NEW` 배지와 토스트도 동작했다. 이상 없음.
(접근성 관련 지적은 `docs/ACCESSIBILITY.md` 8절에 별도로 정리해 두었다.)

## 6. 성능 실측

| 구간 | 실측 |
|---|---|
| `POST /api/call/start` | 1.1 ~ 1.3초 |
| `POST /api/call/turn` | 2.9 / 3.2 / 3.5 / 4.4초 (평균 **3.5초**) |
| `POST /api/call/end` | 1.2초 |
| 응답 음성 페이로드 | base64 **532KB ~ 892KB** (WAV, 4.5~7.6초) |
| 대시보드 반영 | **1.2초** |

턴당 3.5초는 어르신 통화로는 견딜 만하지만 **응답 음성이 base64 WAV 라 페이로드가 크다.**
같은 길이를 MP3 로 주면 1/5~1/10 이 된다. 네트워크가 나쁜 발표장이라면 P6 와 상의할 값이다.

## 7. 녹화 — `docs/images/voisso_e2e.gif`

확장의 `gif_creator` 를 쓸 수 없어, **실제 실행 중 각 단계의 DOM 을 그대로 떠서**(스크립트 제거)
정적으로 렌더링해 프레임을 만들고 이어 붙였다. 화면 내용은 **실서버 응답 그대로**이고,
합성한 것은 프레임 간 타이밍뿐이다. 9프레임 — 대기 → 통화 연결 → 4턴 → 민원카드 → 대시보드 → 새 민원 목록.

## 8. 재현 방법

> **포트 규칙** — `8111` 은 **사용자 미리보기 전용**이다. 쓰지도, 죽이지도 않는다.
> `8000` 은 공용이라 에이전트가 테스트로 점유하지 않는다.
> 에이전트별 전용 포트: P3 8020 · P4 8021 · P5 8022 · P6 8023 · **P7 8024** · P8 8025.
> 아래 재현 절차는 **P7 전용 포트 8024 하나만** 쓴다.

```bash
# 1) 내 전용 포트로 서버를 띄운다 (키는 .env)
python3 -m server --port 8024 &
MY_SERVER=$!                                  # 내가 띄운 PID 만 기억했다가 나중에 정리한다
curl -s localhost:8024/api/health | python3 -m json.tool   # degraded:false 확인

# 2) 사람이 직접 확인하는 경로 (권장)
open http://127.0.0.1:8024/call
#   - 전화 걸기 → 텍스트로 4턴 → 통화 끝내고 민원 접수
#   - 다른 탭에서 http://127.0.0.1:8024/dashboard 를 열어두면 새로고침 없이 뜬다
#   - 소리가 나는지, 마이크 버튼이 권한을 묻는지 반드시 눈/귀로 확인

# 3) 자동 검증 (이 보고서를 만든 방식)
#   계측 스크립트를 넣은 임시 사본을 web/call 안에 만들고(자기 소유 경로),
#   서버의 정적 마운트로 연다. 같은 오리진이라 별도 프록시 포트가 필요 없다.
#     http://127.0.0.1:8024/call/_e2e_tmp.html
#   끝나면 임시 파일과 서버를 반드시 정리한다.
kill $MY_SERVER                               # 남의 프로세스는 절대 건드리지 않는다
rm -f web/call/_e2e_tmp.html
```

> 최초 검증은 공용 서버(8000)와 별도 프록시 포트를 썼다. 포트 배정 규칙이 정해진 뒤
> 위와 같이 **전용 포트 1개** 방식으로 바꿨다. 측정값 자체는 재현 방식과 무관하다.

## 9. 이 검증이 다루지 못한 것

- **실제 마이크 음성이 서버 STT(gpt-4o-transcribe)로 들어가는 경로.** 텍스트 경로만 통과시켰다.
  브라우저 음성인식 경로도 권한 거부까지만 확인했다.
- **사람의 진짜 클릭에서 소리가 나는지.** 2절 참조 — 데모 전 1회 육안·육성 확인 필요.
- 확장 기반 대화형 조작(claude-in-chrome). 연결되지 않았다.
- 동시 통화, 장시간 통화, 네트워크 저하 환경.
